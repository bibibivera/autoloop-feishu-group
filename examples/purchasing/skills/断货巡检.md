# Skill：断货巡检（规则「断货巡检」，卡片发给采购负责人）

写表 notice 一律这样交：`title` 写「写表」，`text` 是 JSON `{"key": "预警编号", "fields": {...}}`，`fyi` 写 true，`key` 写 `row-` 加预警编号加状态。写到哪张表由程序定，你只给字段。

先看资料文件里的 `answers`：空的就是新的一轮，做「巡检」；不空就是采购负责人点了卡片，做「接着干」。

## 巡检（只读）

1. 读 `知识库.md` 里的「断货预警天数」。
2. 用多宝鱼 ERP 的 `purchase_suggestions`（`only_needed` 写 false）拿每个 SKU 的日均销量（velocity）、FBA（fba）、本地仓（local）、在途采购（open_po）、建议采购量（suggest）、供应商名。
3. 可售天数 = (fba + local + open_po) ÷ velocity，保留整数。挑出小于预警天数、且 suggest 大于 0 的 SKU，最多 5 个。没有就结束，第一行写「没事可做：没有可售天数低于预警线的货」。
4. 用 `suppliers_search` 按供应商名查到 supplier_id。
5. 每个 SKU 交一个写表 `notice`（`fyi` 写 true）：
   - `title`：`写表`
   - `text`：一段 JSON：`{"key": "预警-<今天日期>-<SKU>", "fields": {"预警编号": "预警-<今天日期>-<SKU>", "SKU": "...", "商品": "...", "可售天数": 数字, "日均销量": 数字, "建议采购量": 数字, "供应商": "...", "状态": "待决定"}}`
6. 按供应商分组，每个供应商交一个 `ask`（一张卡片一件事）：
   - `title`：不超过 30 字，例如「刮痧板还能卖 78 天，要不要补 67 个」
   - `text`：六段，每段一个加粗小标题：**发生了什么**（可售天数、日均销量、库存构成）、**AI 建议**、**依据**（最多 3 条，最后一条写「还没核：……」）、**方案对比**（建和不建各会怎样）、**同意后将执行**（给哪个供应商建采购单草稿：SKU × 数量，按供应商默认报价）、**截止时间**
   - `options`：`["建采购单", "先不建"]`，`recommend` 写 0
   - `key`：`po-ask-` 加日期和供应商编号
   - `about`：原样写 supplier_id、每行 product_id 和数量、预警编号，接着干时要用

## 接着干

- 选「先不建」：每个预警编号交一个写表 notice，`fields` 只写 `{"状态": "不建"}`。第一行写「好的，这次不建采购单」。
- 选「建采购单」：
  1. `purchase_order_create_prepare`：supplier_id 和 lines 用 `about` 里的；`note` 写「由补货助手创建 · 预警编号……」（测试时加上「测试」两个字）。
  2. 看预览：供应商、数量和卡片上一致才继续；不一致就停，第一行写清哪里不一致。
  3. `action_execute`：action_id 用上一步返回的，confirm 写 `CONFIRM`。只调一次。
  4. `purchase_order_get` 读回：采购单号、状态（应该是草稿）、明细、金额。
  5. 每个预警编号交一个写表 notice：`fields` 写 `{"采购单号": "...", "状态": "已建采购单，待审核"}`。
  6. 在回执的 `events` 里交一个事件，交给审核人：`{"id": "po-created-<采购单 id>", "type": "po.created", "subject": "<采购单 id>", "summary": "采购单 <采购单号> 待审核", "detail": "一段 JSON：采购单 id、采购单号、供应商、明细、金额、预警编号列表、为什么建（两句话）"}`。
  7. 第一行写一句结论：采购单建好了，单号多少，已交给审核人。

不许调用 `purchase_order_submit_prepare`：提交审核是审核人那一步的事。
